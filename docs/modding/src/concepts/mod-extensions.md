# Design: mods extending the mod API

This is a proposed contract for [#2339](https://github.com/arismoko/horizon/issues/2339). None of it is implemented. It covers how a library mod (a chemicals system, an energy network, a machine framework) defines things that other mods use, listen to or extend: **mod hooks**, **mod Part kinds**, **mod services** and **mod registries**. Each section gives the contract, its behaviour on wasm, its NeoForge counterpart and what it costs when nobody uses it. A staged PR plan and the open questions come at the end.

## What exists, and the one fact the design rests on

These already work, read from the code at `54bee0f608`:

- **Plain calls.** A dependent names the library under `[dependencies]` and gets its crate as a Cargo dependency. On native, every code mod is linked into one game binary (`launcher/src/native_mods/api.rs`). On wasm, a library and everything that depends on it form one **dependency group**: one shared memory, one shared table and one copy of each member (`horizon-mod-wasm/src/link.rs`). Two mods that share a library share its group (`groups()` in `horizon-mod-wasm/src/lib.rs`). Calls, statics, generics, trait objects and `Drop` inside a group are ordinary Rust (`tests/real_library.rs`).
- **Mod capability keys.** `CapabilityKey::<dyn ResourceHandler<Chemical>>::new("chemlib:chemical")`, providers through `Registrar`, lookups through `level.capability`. A provider whose handler type belongs to a mod is stored erased (`OwnProvider`, `parts/capabilities.rs`). On wasm, an erased `Arc<dyn Any + Send + Sync>` crosses as a group-scoped resource id. The group that made it gets it back, and any other group gets `wire::Unsupported::CROSS_GROUP` (`wire_resources.rs`, generator `wire/mod.rs` `ERASED`).
- **Hook machinery.** `horizon_mod_runtime::subscribers::Subscribers` builds per-hook lists once at install. Order is priority descending, then dependency order. It also tracks `receive_cancelled` and keeps a bitset for the "anyone listening?" test. `set_mod_enabled` and `mark_mod` handle the player's switch and crash attribution.
- **Typed slot keys.** `BlockKey(u32)` and the other slot keys are backed by `horizon_mod_runtime::registry_keys::Names`: requested at load, then resolved to slots.
- **Attachments.** `AttachmentType<T>` on entity, player, block entity, chunk and level holders, with an optional codec, sync and copy-on-death (`horizon-mod-runtime/src/attachments.rs`). The Part instance state design ([#2328](https://github.com/arismoko/horizon/pull/2328)) makes this the only store for per-instance data.

**The fact:** a mod can name a library's types only if it depends on the library. On native it then sits in the same binary as the library; on wasm it sits in the same group. So within one target, a library-defined value never has to cross the Wire to reach the mods that can use it. The game's job is the part a library cannot do alone: names, ownership, refusals, ordering, the player's on/off switch, crash attribution, lifetimes tied to the server and its levels, and the Mods page. The payload stays in the caller's address space as an erased handle.

What breaks that fact is **mixed targets**: a native library with wasm addons, or the reverse. Those mods are in different address spaces, so anything shared has to go through the game. That case has its own section, and it is the only one that needs mod types to have Wire forms.

### Can a mod give its own types a Wire form today?

No, not in a supported way. `mod_api::wire::Wire` is a public trait, but it is `#[doc(hidden)]` and documented as "not a mod's API" (`exports/wire.rs`). Its impls for `mod_api` types are generated by `horizon-mod-api-gen`, and there is no derive a mod can use. More to the point, nothing on the boundary would carry such a value. Every crossing is a generated call whose signature comes from a `mod_api` trait (the `IMPORTS`/`EXPORTS` lists in `horizon-mod-api-gen/src/wire/mod.rs`), and the layout hash that refuses mismatched builds (`WIRE_LAYOUT`) covers only `mod_api`. A hand-written `impl Wire for Chemical` would compile and never be used.

Within one target this doesn't matter, as shown above. Across targets it does. [Mixed native and wasm mods](#mixed-native-and-wasm-mods) proposes a public `#[derive(mod_api::Wire)]` with a layout hash for each mod.

## 1. Mod hooks

### Contract

A mod hook is a hook in the same sense as a catalog hook or a point under [#2242](https://github.com/arismoko/horizon/pull/2242). It has a listener of the form `fn(&mut <Side>Host, &mut Event)`, a contract, priority and dispatch order. Its name is owned by a mod and not taken from the catalog or from an engine function.

```rust
// chemlib's crate
pub struct TankFilled { pub tank: BlockEntityRef, pub chemical: Chemical, pub amount: u32, pub cancelled: bool }
pub static TANK_FILLED: ModHook<Server, Cancel<TankFilled>> = ModHook::new("chemlib:tank_filled");

fn register(&self, r: &mut dyn Registrar, _: &RegistrationContext) {
    r.declare_hook(&TANK_FILLED);
}
// where a tank fills:
if TANK_FILLED.listened() {
    let mut event = TankFilled { tank, chemical, amount, cancelled: false };
    if TANK_FILLED.post(host, &mut event).cancelled() { return; }
}

// an addon's crate
r.listen(&chemlib::TANK_FILLED, Listen::priority(10).receive_cancelled(), |host, event| { … });
```

The names in the example are only illustrations and still need API review.

| Point | Rule |
|---|---|
| Name | `<declaring mod id>:<path>`. `declare_hook` refuses a namespace other than the declaring mod's id, and refuses a second declaration of the same name, naming both mods. |
| Side | `Server`, `Client` or `Both`, as the catalog's `side`. It fixes the host the listener gets (`&mut dyn ServerHost`, `&mut dyn ClientHost`, or `HostSide`), so a listener on the wrong side doesn't compile. |
| Contract | The catalog's four: `listen`, `cancel` (a `cancelled` field), `collect` (a `Vec` field listeners push to) and `replace` (an `Option` field, where the last writer in dispatch order wins, as the catalog's `out`). Using one set keeps a library's hooks reading like the game's. |
| Registration | `r.listen` during `register`. A mod may listen to one hook more than once, and its listeners keep their registration order, as points tie on inject id. Listening to a name that no loaded mod declares is refused at load, naming both. A listener whose event type differs from the declaration's is refused, naming both types. This is the same check the capability key plan adds for keys. |
| Order | Priority descending, then dependency order, then registration order within the mod. This is `Subscribers`' rule. |
| Cancellation | When a listener cancels, the listeners that follow are skipped unless they registered `receive_cancelled`. Those still run, see `cancelled`, and may clear it. `post` returns the outcome, and the poster decides what cancelling means. |
| Host and transactions | Listeners get the host the poster passed, so their writes run inside the poster's transaction (*every hook gets a `Host`*). |
| Who posts | Any mod that can name the hook. In practice that is the library and its addons. NeoForge doesn't restrict posting either. |
| Lifetime | Declarations and listeners are fixed when registration seals, and the order is resolved once. A mod the player switches off is skipped, through `mod_index_on`, as for catalog hooks. |
| Errors | A native listener's panic is caught and named by the `mark_mod` guard (mod and hook name), as for a catalog hook. A wasm trap stops the group, which is also the library's group. A post nested deeper than 32 levels in the same hook is refused with a log line, not a stack overflow. |

**Points.** Under #2242 a point is a hook named by an engine function path, with a generated record. A mod hook is a hook named by a mod identifier, with a record the mod writes. Both use the same listener shape, contracts, order, switch and refusal style. The one difference is registration. Points are declared in `[[inject]]`, because the game fills compiled slots at load without source. Mod hooks are registered in code, because the library's type is a Cargo dependency anyway. Root decides whether `[[inject]] at = "chemlib:tank_filled"` should also work (question 2).

### On wasm

Nothing crosses at post time. `r.listen` goes through the `Registrar` import, so the game records the owner, the order and the declaration. The listener closure stays in the group as an erased resource (`Arc<dyn Any + Send + Sync>`, the existing `ERASED` form). When registration seals, the game makes one load-phase call per group that declared hooks, handing it the resolved order. All listeners are in that group by construction. `post` then walks that list in the group's own memory. Switching a mod on or off makes one call into each group concerned to update its bitset. `TankFilled` never needs a Wire form. The only refusal is the mixed-target case below.

### NeoForge

A NeoForge library defines `class TankFilledEvent extends Event implements ICancellableEvent` and posts it with `NeoForge.EVENT_BUS.post(event)` or on its own bus. Listeners use `@SubscribeEvent(priority = …, receiveCanceled = true)` or `bus.addListener(priority, receiveCanceled, TankFilledEvent.class, consumer)`. The [public events guide](https://docs.neoforged.net/docs/concepts/events/) documents `ICancellableEvent` and `receiveCanceled`. It is labelled 26.1, so 26.3 equivalence is **unverified**. Differences: NeoForge has five `EventPriority` steps where Horizon uses `i32`, as catalog hooks already do. NeoForge dispatches by event class where Horizon uses a declared name, because a name can be refused, shown and checked for type agreement. A Java listener for an event nobody posts is silently never called, while Horizon refuses it.

### Cost when unused

`listened()` is one load of a per-hook word, resolved into the `ModHook` static once after sealing. A library that guards construction with it builds nothing. `post` with no listeners returns at once. Neither target crosses the boundary or allocates, and no mod is scanned. A library with no hooks costs nothing.

## 2. Mod Part kinds

### Contract

A Part kind is a trait the library defines, plus a name, plus what its parts attach to. Addons implement the trait and attach it. The library asks the attached parts at its own moments.

```rust
pub trait Reactor: Send + Sync + 'static { fn react(&self, host: &mut dyn ServerHost, input: &Chemical) -> Option<Chemical>; }
pub static REACTORS: PartKind<dyn Reactor> = PartKind::new("chemlib:reactor", Scope::BlockEntityType);
// chemlib: r.declare_part_kind(&REACTORS);
// addon:   r.attach(&chemlib::REACTORS, Target::id("addon:fusion_chamber"), FusionReactor);
// chemlib, at its moment:
for reactor in REACTORS.parts(host, block_entity_type) { … }
```

| Point | Rule |
|---|---|
| Name | Namespaced by the declaring mod, declared once, with the same refusals as hooks. |
| Scope | What a part attaches to. It can be one of the holder kinds Parts use today (block, block entity type, item, entity type, fluid, menu type) or a mod registry (section 4), such as `Scope::Registry(&CHEMICALS)`, for behaviour attached to a chemical. Attaching to an id of the wrong kind, or to an id that doesn't exist, is refused, naming both. Note that `capability()` today returns silently for an unknown block entity type. |
| Targets | An id or a tag. Tags are resolved by each game at world open and on `/reload`, as built-in parts are, into a table keyed by slot. |
| Multiplicity | One part of each concrete type per kind and thing, the existing `insert_part` rule and message. Different mods' parts on one thing are all kept. |
| Order | Dependency order, then registration order within a mod, as `Attached` keeps it. |
| Contract | The library's own. `parts()` yields the parts in order, and the library decides whether all of them run, the first answer wins, or anything else. Part kind methods are part of the library's API, as `IPart` is AE2's. |
| State | Parts are shared behaviour. Data for each instance lives in attachments, as #2328 proposes. |
| Lifetime | Attached during `register` and frozen when it seals. The resolved table is rebuilt at world open and on `/reload`, and an iterator never outlives the call it was made in. |

A Part kind and a capability key share storage but answer different questions. A capability is "who answers this, from this side", with the first answer winning and possibly a default from the game. A Part kind is "every behaviour attached to this thing". Both should be built on one erased parts table (`Attached<dyn Any>`), not two. Whether `CapabilityKey` becomes a Part kind with a context is question 3.

### On wasm

This works like `OwnProvider` today. The part is an erased resource in the attaching mod's group, which is also the library's group. The game keeps (kind, target, owner, order, handle). At world open and on `/reload`, it hands each group that declared kinds the resolved table in one load-phase call. `parts()` reads that table in the group without crossing. Nothing of the library's type crosses.

### NeoForge

There is no first-class counterpart, and #41's Parts are already a fork addition. In NeoForge this is a library convention: AE2's `IPart` with `PartItem` for cable-bus parts that addons implement, Create's `BlockEntityBehaviour` and `BehaviourType`, and Mekanism's module registry. Capabilities (`BlockCapability.createSided` plus `RegisterCapabilitiesEvent`) are the platform's nearest mechanism, and they map to `CapabilityKey`. Horizon gives every library the same table, the same refusals and tag resolution in place of hand-rolled maps.

### Cost when unused

None if no kind is declared: no tables and no world-open call. A declared kind with no parts makes `parts()` one slot index into an empty slice. Resolution scales with the number of attachments, not with ticks.

## 3. Mod services

Plain calls already cover a stateless library API. A service is for the two things plain calls get wrong.

**Scoped state.** A library that keeps a manager in a `static` shares it between the client thread and the server thread in single player, which runs on a server thread (#1514). The state also outlives the world when the player leaves and reopens it. Scoped state ties the object to the host's own lifetime:

```rust
pub static NETWORKS: Scoped<Server, Networks> = Scoped::new("chemlib:networks", Networks::default);
NETWORKS.get_mut(host)  // reached only through a ServerHost
```

| Scope | Created | Dropped | Reached through |
|---|---|---|---|
| `Server` | on first use after `server_about_to_start` | after `server_stopped` | `ServerHost` |
| `Level` | on first use in a loaded level | after that level's `level_unload` | `ServerHost` plus `LevelRef` |
| `ClientSession` | on first use after the client logs in | after `ClientPlayerNetworkEvent.LoggingOut` | `ClientHost` |

- **No new lifecycle callbacks.** A library that wants to act at a scope's start or end listens to the existing hooks named in the table (one hook per moment).
- **Not saved.** Saved data goes through attachments. A level-scoped state saves through `AttachmentType` on `AttachmentHolder::Level`, which is NeoForge's `SavedData` on a level. Server-wide saved data has no holder today; question 4 asks whether to add `AttachmentHolder::Server`. A service keeps runtime state (graphs, caches, indexes) and rebuilds it from attachments when its scope starts.
- **Threads and types.** `T: Send + 'static`. Only the scope's thread reaches it, which the host type enforces, so `T` needn't be `Sync`.
- **Names.** Namespaced by the declaring mod, declared once, with the same refusals as hooks.

**Service interfaces.** An API mod (types and a key, no implementation) declares `pub static GRID: ServiceKey<dyn EnergyGrid>`. One implementing mod depends on it and calls `r.provide(&GRID, scope, factory)`. Consumers depend only on the API mod and call `GRID.get(host) -> Option<&dyn EnergyGrid>`.

- A second provider is refused at load, naming both mods.
- With no provider installed, `get` returns `None`. A consumer that requires the service says so with `ServiceKey::required`, and it is then refused at load naming the key, not left to fail at run time.
- The provided object is scoped like `Scoped`.

Whether a provider may replace another one (an optimisation mod taking over a library's default) is question 5.

### On wasm

The object is an erased resource in the group. Scope identity comes from the host: the server session's `WorldEpoch`, a `LevelRef`, or the client session. The group keeps a map from scope identity to handle. At each scope end, the game calls each group that declared a service of that scope once, to drop the entries for that scope. A lookup costs one host read for the scope identity, which the group caches per call. Nothing of the library's type crosses.

### NeoForge

NeoForge has no service type. Libraries combine Java `ServiceLoader` (an API jar with one implementation found at run time), `InterModComms` messages at load, `SavedData` (`level.getDataStorage().computeIfAbsent(…)`, with the overworld's storage for server-wide data) and data attachments on levels. Scoped state plus attachments covers `SavedData`. `ServiceKey` covers the `ServiceLoader` pattern, and adds a load-time refusal for two providers or a missing required one where Java just picks one. IMC isn't needed, because dependents call the library directly in dependency order.

### Cost when unused

None. Nothing is created until first use, and the scope-end calls go only to groups that declared services. On native a lookup is a slot index into the host's table.

## 4. Mod registries (code-defined)

### Contract

```rust
pub static CHEMICALS: ModRegistry<Chemical> = ModRegistry::new("chemlib:chemical");
// chemlib: r.declare_registry(&CHEMICALS, RegistryOptions { sync: RegistrySync::Names, default: Some("chemlib:empty") });
// addon:   let PLASMA: RegistryEntry<Chemical> = r.register(&CHEMICALS, "addon:plasma", Chemical::gas(0xff00ff));
CHEMICALS.get(PLASMA) / CHEMICALS.by_name("addon:plasma") / CHEMICALS.iter()
```

| Point | Rule |
|---|---|
| Registry name | Namespaced by the declaring mod, declared once (refused otherwise, naming both). It shares one key space with the game's registries and with #2332's data-pack registries, and a collision with either is refused. |
| Entries | Named in the registering mod's own namespace, which is refused otherwise, as #2332 proposes. A duplicate entry name is refused, naming both mods. `register` returns a typed `RegistryEntry<T>` slot key, the same kind of key as `BlockKey`. |
| Order | Dependency order already makes the library's `declare_registry` run before any dependent's `register`, so one registration phase is enough. NeoForge needs `NewRegistryEvent` before `RegisterEvent` only because Java mods have no declared dependency order. |
| Freezing | The registry is frozen when registration seals. After sealing, the library builds its derived tables in a listener of the first lifecycle hook after registration. Which hook that is, and whether it needs a dedicated "registries frozen" hook with no NeoForge name, is question 6. |
| Slots | Fixed when registration seals and local to the session. Saves store names, never slots, as #2332 requires. A save naming an entry that is no longer registered follows #2336's quarantine rule. |
| Clients | With `RegistrySync::Names`, the server sends name→slot during configuration and the client remaps, as NeoForge's `sync(true)` does. Values aren't sent: both sides ran the same code. A client missing the declaring mod is refused at join with the registry named. `RegistrySync::None` registries are server-only. |
| Tags | `data/<ns>/tags/<registry ns>/<registry path>/…`, through the existing tag loader. Part kinds (section 2) can target these tags. |
| Data packs | A code registry has no entries from data packs. A registry whose entries come from data is #2332's. #2332 entries may refer to code-registry entries by name, resolved on the game side. |

### On wasm

The game keeps names, slots, owners and tags. Values stay in the group as erased resources: each value is registered by a group member, and the library is in that group. When registration seals, the group receives the slot order in one call. `get` is then an index into the group's own table. Names and slots are strings and `u32`s, so they already cross. Nothing of the library's type crosses.

### NeoForge

`RegistryBuilder<T>(ResourceKey<Registry<T>>)` with `.sync(true)`, `.defaultKey(…)` and callbacks, registered in `NewRegistryEvent` or with `DeferredRegister.makeRegistry`. Entries come from `DeferredRegister.create(key, modid)` and `RegisterEvent`. Sources: the [public registries guide](https://docs.neoforged.net/docs/concepts/registries/), labelled 26.1, and the 26.1 `DeferredRegister.makeRegistry` javadoc. 26.3 is **unverified**. Differences: there is one phase in place of two, for the reason above. Entry namespaces are enforced. A missing client mod is refused by registry name.

### Cost when unused

None without a declaration: nothing is added to configuration or the tag loader. Reads are an index. Seal and sync work scales with the number of entries, once per session.

## Mixed native and wasm mods

Native and wasm mods can't call each other's functions: they live in different address spaces. Today a wasm mod whose dependency is a native mod is refused at load. `groups()` resolves over the wasm packages only, so it reports `MissingDependency` ("needs X, which isn't installed"), which is misleading. The reverse direction wasn't traced: whether the launcher's native build would compile a wasm library's source natively is **not checked**. This design proposes:

**Rule.** A library is loaded on exactly one target. An addon on the other target may still depend on it, but only through extension points that go through the game. It never links the library's code.

| Extension point | Across targets |
|---|---|
| Plain calls, statics, generics | **Refused at load** with "chemlib is a native mod; wasm mod X calls its code". On wasm this is an unresolved library symbol, which `link.rs` already refuses, with a better message. On native it is a link error at build time. |
| Mod hooks | **Work** if the event type has a Wire form (below). The game forwards the encoded event between the poster's target and the listeners on the other one, and the listeners' changes come back. Order and cancellation follow one merged list. A hook whose event has no Wire form refuses cross-target listeners at load, naming the type. |
| Mod registries | **Work for names and slots**, which the game owns. A cross-target mod reads an entry's value only if `T` has a Wire form: the value is encoded once when registration seals and decoded into the reader's own copy. Otherwise the read is refused at load. |
| Capabilities, Part kinds, service interfaces | **Refused at load** in the first stages. A handler is a trait object, and calling it across targets needs the trait's methods to be generated as boundary calls, as the generator does for `mod_api`'s `EXPORTS`. That would come later, as an opt-in `#[mod_api::extension]` on the library's trait, which requires every argument to have a Wire form. Until then, the refusal names the trait. |
| Scoped state | Never shared across targets. Each target holding its own copy would give two diverging states, so it is refused, naming the key. |

**Wire forms for mod types.** A public `#[derive(mod_api::Wire)]` (in `horizon-mod-api-macros`) emits the same encoding the generator emits for `mod_api` types: fields in order, `u32` enum cases, and the same reader checks and limits. Each mod with derived types gets its own layout hash, recorded in its manifest. A cross-target dependent built against another layout is refused at load, as `Refusal::Layout` does for `mod_api`. The game never decodes a mod's type. It only forwards bytes and checks the hash. Within one target the derive changes nothing.

**What a cross-target addon compiles against.** It needs the library's types and keys without its code. That means the library publishes them in a crate that holds no state (types, keys, traits, Wire derives). Whether that becomes a declared part of the package model, or mixed targets are refused outright, is question 1. The existing rule *one dependency model, two build targets* means whichever is chosen has to hold for both targets.

## Where it lives after the restructure

Following the domain modules in the `mod_api` restructure: `ModHook`, `Listen` and `Scoped`/`ServiceKey` go in `runtime`, beside `Flow`, `listened` and the mod list. `ModRegistry` and `RegistryEntry` go in `content`, beside the registry keys. `PartKind` goes beside the Parts it shares a table with. The `Registrar` methods (`declare_*`, `listen`, `attach`, `provide`, `register`) are generated like the other registrar methods.

## Open questions for root

1. **Mixed targets.** Should a native library with wasm addons (or the reverse) be supported through the game, as proposed above? That needs a stateless "types crate" in the package model. The alternative is refusing mixed targets outright with a clear message. Recommendation: land the clear refusals first (stage 6a) and decide the types crate when a real library needs it.
2. **`[[inject]]` for mod hooks.** Should mod hooks also be listenable through `[[inject]] at = "<mod>:<hook>"`, which would make points and mod hooks one manifest model? Recommendation: code registration only, since it is typed and needs no slot.
3. **Capability keys and Part kinds.** Should `CapabilityKey` be merged into `PartKind` (a part kind with a context and first-answer lookup)? Recommendation: keep NeoForge's name and API for capabilities and share only the storage.
4. **Server-wide saved data.** Should `AttachmentHolder::Server` be added for state that belongs to a server and not a level? NeoForge uses the overworld's storage.
5. **Replacing a service provider.** May a mod override another mod's service provider? Recommendation: no, refuse two providers, until a concrete case exists.
6. **The "registries frozen" moment.** Which existing hook is the first after registration seals? If none fits, a Horizon-only hook is needed.
7. **Owner question, no recommendation:** should addons ever be able to patch another mod's code, as NeoForge mixins can target other mods' classes? Or should they only use the extension points a library offers?
