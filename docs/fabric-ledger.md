# Fabric API mapping ledger

This is a porting ledger, not a promise of binary or source compatibility. **Covered** means the named use has a usable counterpart, not that a whole Fabric module is identical. **Planned** means an explicitly identified design or tracker item, not shipped code. **Gap** means the particular semantics have no established equivalent. Multiple statuses on a row distinguish the individual claims.

Reference: Fabric API 26.3 branch at [`2065040b236a0d5ac011bd6a45625dc49579b222`](https://github.com/FabricMC/fabric/tree/2065040b236a0d5ac011bd6a45625dc49579b222) (Apache-2.0); fork main `be1fa0d1ec89d07998e8ea7c72137ce483904d8c` (snapshot, not a current-status guarantee). NeoForge names below refer to its public 26.3 API, not its implementation: [`ResourceHandler`](https://aldak.netlify.app/javadoc/26.3.x/net/neoforged/neoforge/transfer/ResourceHandler.html), [`Transaction`](https://aldak.netlify.app/javadoc/26.3.x/net/neoforged/neoforge/transfer/transaction/Transaction.html), [`TransactionContext`](https://aldak.netlify.app/javadoc/26.3.x/net/neoforged/neoforge/transfer/transaction/TransactionContext.html), and [`SnapshotJournal`](https://aldak.netlify.app/javadoc/26.3.x/net/neoforged/neoforge/transfer/transaction/SnapshotJournal.html). The fork's parts contract is #41 §7. Paths below are relative to the repository.

## Transfer: `fabric-transfer-api-v1`

| Fabric API | Purpose | NeoForge counterpart | Fork counterpart and status | Material differences |
|---|---|---|---|---|
| `Storage<T>` | Insert/extract a resource and inspect a storage; capability/support queries and a version hint. | `ResourceHandler<T>` | **Covered in part:** `ItemHandler`, `ITEMS` (`crates/horizon-client/src/mod_api/capability.rs`); `FluidHandler`, `FLUIDS` (`crates/horizon-client/src/mod_api/fluid_capability.rs`); item-held items `StackItemHandler`, `ITEM_ITEMS` (`crates/horizon-client/src/mod_api/item_place.rs`). | Fabric is generic, returns accepted/extracted `long` amounts and requires transaction contexts; NeoForge's `ResourceHandler` also uses `TransactionContext`. Fork handlers expose numbered slots/tanks, return remaining/extracted stacks and use `u32` amounts and `simulate`; support and version hints have no direct equivalent. No generic Fabric adapter is implied. |
| `StorageView<T>`, `iterator()`, `nonEmptyIterator()`, `nonEmptyViews()` | Inspect each resource, amount and capacity and extract from a view; nonempty iteration filters blank/zero views. | `ResourceHandler<T>` indexed resource and capacity access | **Covered in part:** `slots`/`stack` and `tanks`/`fluid` plus `capacity` in the handler files above; **gap:** Fabric view/iterator contract and underlying-view identity. | Fabric may visit a resource more than once; extraction during iteration must be visible, insertions need not be; a changed iterator may become invalid at outer transaction end. Index traversal and `Option` filtering are an approximation, not those guarantees. Fork capacity asks about a supplied stack in an empty slot/tank; it is not directly a blank view's estimated bound. |
| `Transaction`, `TransactionContext`, nested `openNested`, commit and abort | Tentative, composable changes across participants; closing without commit aborts, inner commit remains subject to outer abort. | `Transaction`, `TransactionContext`, `SnapshotJournal` | **Gap:** no nested transaction/rollback API. `simulate` in the handler traits is a non-mutating plan and must predict the real call; #41 §7 defines capability parts, not transactional atomicity. | A truthful single simulation gives a no-write preview, and a subsequent unchanged-state real call must give the same result. It does **not** stage a series of changes, make subsequent operations see tentative state, roll back a committed operation, or provide atomic all-or-nothing multi-handler/nested operations. Compensation on a bad handler is best effort, not rollback. A Fabric-style mod requiring these guarantees needs a transactional participant/snapshot or staged-write layer across every involved storage, including item exchange and outer/inner commit; simulations alone cannot implement it. |
| `FluidVariant`, `ItemVariant` | Resource identity and components separated from the transferred quantity. | `FluidResource`, `ItemResource` | **Covered in part:** `FluidStack` (`fluid_capability.rs`) and `ItemStack` with components (`mod_api`); identity comparators `same_fluid_same_components` and `same_item_same_components`. | Fork stacks combine identity and quantity, while variants have no amount and have blank variants. Retain component identity when adapting, do not compare only IDs. Current default item-fluid plan rejects component-bearing fluids rather than preserving them. |
| `FluidConstants` | Amounts in droplets: 81,000 per bucket. | Fluid quantities in millibuckets | **Covered in part:** `FluidStack.amount` is `u32` mB, 1,000 per bucket (`fluid_capability.rs`). | 81 droplets = 1 mB. Arbitrary droplet amounts, including one droplet, cannot be represented exactly as integer mB; Fabric `long` range also exceeds `u32`. Reject or explicitly negotiate loss; silent rounding changes recipes and can create or destroy fluid. |
| `FluidStorage.SIDED` | Lookup a block storage by position and optional direction; null means unrestricted. | `Capabilities.Fluid.BLOCK` | **Covered in part:** `Host::capability(&FLUIDS, pos)` and handler calls with `Option<Direction>` (`capability.rs`, `fluid_capability.rs`); mod registration in `part_table.rs`. | Direction is passed to each handler method, not to lookup. The default covers mod tanks and cauldrons; a block capability key is not a Fabric lookup object and does not imply identical provider composition, invalidation or client behavior. |
| `FluidStorage.ITEM` | Query item fluid storage using a container context; Fabric provides buckets and water potions and supports combined providers. | `Capabilities.Fluid.ITEM`, `ItemAccess` | **Planned:** `ITEM_FLUIDS`, `StackFluidHandler`, `Host::item_capability` and default as described in the ITEM_FLUIDS plan; not shipped at this snapshot. | The plan handles plain water/lava buckets and configured mod tanks, not water potions or arbitrary bidirectional fluid buckets. One registered part replaces the default, unlike Fabric's combined providers. The plan rejects component-bearing fluid in its default; transactions and exact droplet granularity remain gaps. |
| `ContainerItemContext` | Main slot, overflow and additional slots, exchange items transactionally; contexts include hand, cursor, single slot, creative and constant. | `ItemAccess`, particularly `exchange` | **Covered in part:** `ItemPlace`, `PlaceProvider`, `Host::place_stack`, `Host::set_place_stack`, `Host::item_capability` (`item_place.rs`); **planned:** use with `ITEM_FLUIDS`. | `ItemPlace` locates a stack and can split a changed item; hand overflow may drop and a block slot can refuse if no room. This is not Fabric's general transactional main/overflow/additional-slot API or its creative/constant context. Validate the current item before use. |
| `StorageUtil.move` | Filter resource variants and move up to a `long` total, using nested transactions, with optional enclosing transaction. | `ResourceHandler` transactional operations | **Covered in part:** `Host::transfer_fluids` (`fluid_capability.rs`, #87/#98); the existing `native_move_items` helper, described in `docs/native-mods.md`. **Planned:** item/block fluid moves in the ITEM_FLUIDS plan. | Fork transfer plans and commits in rounds and compensates best effort when handlers disagree; it is not caller-abortable and has no enclosing transaction. Fabric's filter and potentially multiple variants in one call are not implied by the fork helper. Mismatch may require returning material, and fluid may be lost with a warning if neither end accepts it. |
| Team Reborn Energy `EnergyStorage` (separate project, not Fabric API) | Electric energy storage and transfer on Fabric. | `Capabilities.Energy.BLOCK` / `ITEM`, `EnergyHandler` | **Planned:** #41 §7 `ENERGY` and `ITEM_ENERGY`, game defaults over `block_entity_energy` and `item_energy_buffer`; block and item handlers are not claimed shipped. | Energy is not `fabric-transfer-api-v1`; verify Team Reborn's own version, units and transaction semantics before implementing an adapter. Neither a unit conversion nor transactional parity follows from an energy capability name. |

### Design recommendations for item fluids and energy

1. Keep a place-backed item exchange and simulate its split/overflow with the exact operation that commits; document the different creative, overflow and water-potion behavior rather than calling it Fabric parity. Allow a deliberate provider composition strategy if several mods need to expose one item.
2. Preserve resource components end-to-end for handlers that support them; make the default's refusal explicit. Decide how to represent droplets not divisible by 81 and amounts exceeding `u32` before promising lossless Fabric ports.
3. The parts contract needs transactions to meet the NeoForge floor, not only for Fabric: specify a shared transaction/staging contract for all participating block and item fluid/energy handlers, nested savepoints and outer rollback, including overflow and callbacks. Until then expose the plan/commit limitation prominently, and do not promise atomic Fabric `StorageUtil.move`.
4. For ENERGY and ITEM_ENERGY, document units, range, side semantics, capacity, simulation and item replacement independently; inspect the chosen Team Reborn release before claiming compatibility. Provide view and filtering adapters only with clearly stated iteration and identity limits.

## Lifecycle, networking and registries

The status applies to the named surface, not the whole module. A Fabric callback and a NeoForge event at the same firing point should share one hook; do not add a second hook just because their names differ. Where timing, side, payload or cancellation differs, the remaining contract is still a gap.

| Fabric module and key API | Fork mapping and status | Porting boundary |
|---|---|---|

Chunk, block-entity and client lifecycle callbacks are not all proven by those names. Entity join timing/portal caveats are documented in #27. |
| `fabric-networking-api-v1`: `PayloadTypeRegistry`, `ServerPlayNetworking`, `ClientPlayNetworking`, login/configuration/play connection events, `PlayerLookup` | **Covered in part:** `native_net_send_to_player`, `native_net_send_to_server`, `native_net_from_client`, `native_net_from_server` (`docs/native-mods.md`, Mod messages); `player_login`, `server_players`, `client_level_load`/`unload`. **Gap:** no claim that every Fabric login/configuration/play payload registration, phase, channel negotiation or connection event is equivalent. | Check direction, connection phase, codec, thread, tracking recipients and disconnect handling.
